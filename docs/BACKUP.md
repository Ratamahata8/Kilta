# Резервирование Supabase и восстановление

Git содержит приложение, миграции и статическую сборку. Он **не содержит** пользовательский контент Supabase, Auth и Storage. Владелец данных и разработчик должны согласовать периодичность, хранение, регион, сроки и доступы к бэкапам до production.

## Что сохранять

1. PostgreSQL: `user_roles`, `content`, `published_content`, `versions`, таблицы ссылок, `media`, `published_media`, `inquiries`. История и UUID нужны для ссылок и неизменяемых редакций. Auth user IDs тоже должны сохраняться/сопоставляться при переносе.
2. Файлы **всех четырёх buckets**, включая оригиналы, производные WebP, PDFs и исторические публичные копии. Сохраняйте полные имена объектов, MIME, размер и контрольные суммы.
3. Настройки проекта: signup off, Site URL, redirects, buckets/private flags/MIME/size limits, policies/grants/RPC. Секреты отдельно в менеджере секретов, не в git и не в публичном архиве.

Проверьте, что выбранный тариф Supabase включает нужные DB backups/PITR и способы выгрузки. Database backup не гарантирует копирование bytes Storage; отдельно убедитесь в составе backup по актуальной документации Supabase.

## Рабочая процедура разработчика

- Используйте поддерживаемый Supabase DB backup/dump процесс и официальный Storage/S3-compatible экспорт. Credentials передавайте через защищённое окружение/менеджер секретов. Никогда не вводите service_role или DB password в frontend или публичные Actions logs.
- Для DB dump через CLI сначала проверьте охват схем (`public`, необходимые `auth` данные и права) и совместимость восстановления с управляемым проектом. Не восстанавливайте `storage.objects` отдельно, подменяя им файлы: это метаданные, а не bytes.
- Для Storage выгрузите объекты через авторизованный Storage API/поддерживаемый экспорт, пройдите все страницы списка и сформируйте manifest: bucket, key, MIME, length, SHA-256. Храните архив зашифрованным с ограниченным доступом. Public bucket в архиве не означает, что private bucket тоже можно сделать публичным.

## Проверка восстановления — отдельный тестовый проект

1. Создайте изолированный управляемый проект с совместимой версией PostgreSQL/Storage, согласованным регионом и достаточной квотой.
2. Восстановите DB/миграции и Auth штатным для Supabase способом. При переносе с изменением Auth UUID перепривяжите `user_roles` и авторов по проверенному mapping; не копируйте старые session tokens.
3. Восстановите реальные bytes в buckets с теми же ключами/типами, восстановите private/public flags, размерные ограничения и policies. Проверьте SHA-256 и размеры относительно manifest; не достаточно считать строки `storage.objects`.
4. Отключите signup, настройте Site URL/redirects. Соберите отдельную тестовую frontend-версию с URL/publishable key нового проекта. Не подменяйте production настройки ради пробы.
5. Пройдите реальный вход owner, загрузку, draft isolation, анонимные allow/deny Data API и Storage, публикацию, историю/восстановление документа и неизменность адреса. Проверьте private original и обе публичные WebP-копии. Убедитесь, что посетитель не видит черновик и заявки.
6. Зафиксируйте дату, ответственного, число записей/файлов, сверку hashes и результаты сценариев. Только после такой проверки называть backup восстановимым.

Облачное backup/restore в этой сессии **не выполнено**: реальный проект и credentials не предоставлены. Изолированные SQL-тесты подтверждают миграцию/RLS и идемпотентность seed, не восстановление облачных файлов/Auth.

## Обновление и откат frontend

Для обновления выполняется Pages workflow; миграции и seed автоматически не запускаются. Контент и файлы остаются в Supabase. Для отката примените предыдущую проверенную статическую сборку/commit в отдельном review-процессе, сохранив публичные параметры нужного проекта. Сначала убедитесь в совместимости старого frontend с текущими RPC/схемой. Не откатывайте БД/не стирайте файлы вместе с JS и не запускайте seed поверх пользовательского контента. Изменения схемы версионируйте отдельными additive migrations, предварительно проверяя backup и staging.
