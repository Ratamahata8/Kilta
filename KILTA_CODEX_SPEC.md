# KILTA — GitHub Pages + Supabase: задание для Codex (редакция 2)

## Результат

Создай в этом репозитории работающий сайт авторской мебели и скульптур KILTA с настоящей русскоязычной админкой. Заказчик должен войти через браузер, загрузить свои фотографии и арты, наполнить каталог, изменить тексты и документы, выбрать оформление и опубликовать изменения без GitHub, терминала и помощи разработчика.

## Приоритет архитектуры — заменяет прежнее задание

Публичный сайт И интерфейс админки должны работать на GitHub Pages. Не использовать Next.js server runtime, Payload CMS, VPS, Caddy, Docker deployment или отдельный постоянно работающий сервер приложения. Сохрани уже сделанную работу отдельным коммитом/веткой и адаптируй полезные компоненты; не продолжай прежнюю архитектуру.

GitHub Pages хранит только статическую сборку. Для реальной авторизации, сохранения контента и файлов использовать внешний управляемый Supabase (Auth + PostgreSQL/Data API + Storage). Это обязательная внешняя зависимость; не имитировать её localStorage. Заказчик работает в нашей русскоязычной админке и не должен пользоваться GitHub или панелью Supabase. Настройку Supabase один раз делает разработчик.

Репозиторий не менять на публичный автоматически. GitHub Pages из private-репозитория требует подходящего платного плана GitHub. На GitHub Free можно использовать public-репозиторий с исходниками либо отдельный public-репозиторий только со сборкой; выбор и раскрытие материалов согласовать с владельцем. По умолчанию подготовить Pages deployment для текущего репозитория и описать ограничение тарифа. Public-сайт и private-код — разные настройки. Любой код и изображения, отправленные в публичный браузер, остаются доступны посетителю.

Это реализация, а не только план. Если Supabase не подключён, реализуй все интерфейсы, интеграцию, SQL-миграции и deployment, проверь статическую сборку, перечисли конкретные недостающие параметры. Отдельный read-only demo mode с явной надписью допустим, но не выдавать его за работающую админку. Не утверждай, что данные сохраняются между устройствами, пока не проверена настоящая интеграция.

## Стек и размещение

- React, TypeScript, Vite, @supabase/supabase-js; CSS variables и один последовательный способ стилизации.
- Маршрутизация через HashRouter, чтобы прямые ссылки не требовали серверных rewrite: главная `/#/`, каталог `/#/catalog`, предмет `/#/products/slug`, админка `/#/admin`. При project Pages добавить base `/Kilta/`; имя и регистр брать из фактического репозитория. Не обещать чистый путь `/admin` на Pages.
- Ресурсы и ссылки должны работать и на project Pages, и на корневом custom domain; base задаётся конфигурацией окружения.
- Supabase Auth: email/password, отключённая публичная регистрация; владелец создаётся разработчиком. Реальные права в PostgreSQL RLS и Storage policies.
- Контент читать из Supabase во время работы сайта, поэтому публикация из админки видна на другом устройстве после обновления страницы без коммита и пересборки. Не обещать мгновенное обновление уже открытых вкладок без реализации подписок.
- GitHub Actions: npm ci, typecheck, lint, build, upload Pages artifact, deploy Pages официальными actions. Минимальные permissions, environment github-pages, concurrency. Deploy при push в основную ветку и workflow_dispatch.
- Только URL проекта и публичный publishable key (или legacy anon key с корректными policies) могут попасть в VITE_* и клиентский bundle. service_role, secret keys, пароли БД и почтовые секреты — никогда. Размещение public key в GitHub Secrets не делает его секретным после сборки.
- Подготовь `.env.example`, совместимые закреплённые зависимости и lockfile. Не требуй Docker для запуска фронтенда, сборки или работы опубликованного сайта. Локальные backend-тесты с Supabase CLI могут опционально требовать Docker; это отдельно описать, не делать обязательным для владельца.

## Дизайн и страницы

Основа — концепт «Светлая галерея»: молочный фон #F5F3EE, графит #252525, крупные фотографии, выразительные заголовки, спокойные подписи, много пространства. Образцы макетов, если приложены, являются визуальными референсами, а не фоном страницы. Воспроизведи дизайн живыми компонентами.

Дополнительно реализуй темы «Тёплая мастерская» (песочный #E8DDCD, коричневый #49382C, терракотовые акценты) и «Тёмный арт-каталог» (угольный #171717, текст #EEE9DF, бронзовые акценты). Выбор активной темы — в админке. Общая структура сайта остаётся стабильной. Применяй тему без пересборки; проверяй контраст текста и кнопок во всех темах.

Страницы:
- Главная: меню, крупный первый экран с изображением и текстом, кнопки «Смотреть коллекцию» и «Обсудить заказ», избранные предметы, категории, семейная мастерская, индивидуальный заказ, шоурумы, подвал.
- Каталог с категориями и простыми фильтрами по наличию, материалу и диапазону цены. Предметы без открытой цены корректно показываются как «Цена по запросу».
- Карточка предмета: галерея, название, описание, материал, размеры, стоимость/цена по запросу, наличие, срок изготовления, индивидуальные варианты, кнопка обращения.
- Мастерская / о нас.
- Шоурумы: адреса, контакты, ссылка на маршрут, предметы в конкретном шоуруме. Внешняя карта загружается только по действию пользователя.
- Контакты.
- Документы: политика, согласие, оферта при необходимости, доставка и оплата, возврат и гарантия, реквизиты, информация о cookie.
- Страница 404, пустые состояния, обработка ошибок.
- Админка `/#/admin` с авторизацией (под base репозитория).

Категории на старт: шезлонги, скульптуры, консоли, комоды, ширмы, столы, стеллажи, торшеры. Заказчик может менять список.

На телефоне используй удобное меню, читаемые подписи, адаптивную галерею, доступные кнопки. Не добавляй тяжёлое видео на первый экран, принудительную анимацию, декоративные заглушки вместо фотографий. Учитывай prefers-reduced-motion.

## Контент в CMS

### Коллекции

1. **Пользователи**: email, имя, роль `developer` / `owner`. Создание пользователей выполняется разработчиком через Supabase Dashboard или защищённый административный инструмент; не через service_role в браузере. Только developer управляет ролями. Owner управляет контентом и собственным профилем, не может назначить себе другую роль.
2. **Медиа**: файл, alt, подпись, автор/источник при необходимости, focal point. Загрузка JPEG, PNG, WebP и AVIF при поддержке используемого обработчика. Ограничение изображения 20 МБ, проверка разрешённых MIME и лимита в Storage, попытка декодировать изображение; если полная серверная проверка не реализована, явно указать ограничение. SVG не принимать по умолчанию. Создавай оптимизированные производные изображения в браузере перед загрузкой, сохраняй оригинал; не зависеть от платных image transforms. Проверку файлов и права не ограничивать клиентской валидацией. Заказчик может загружать несколько файлов, выбирать существующие и менять порядок фотографий. PDF документов хранить отдельно с лимитом 10 МБ.
3. **Категории**: название, slug, изображение, описание, порядок, статус публикации.
4. **Предметы**: название, slug, категории, основное изображение, галерея, rich text описание, материалы, высота/ширина/глубина с единицами, режим цены (точная / от / по запросу), сумма, валюта RUB, наличие (в наличии / под заказ / продано), срок изготовления как текст, варианты исполнения, избранное, порядок, SEO. Черновики и версии с отдельным опубликованным снимком; редактирование опубликованной записи не раскрывает новые правки до публикации.
5. **Шоурумы**: название, город, адрес, часы работы, контакты, фотографии, проверенная владельцем ссылка маршрута, связанные предметы, порядок, статус.
6. **Документы**: тип, название, slug, текст в rich text, дата редакции, дата вступления в действие, необязательный PDF, показывать в подвале, порядок. Черновики, предпросмотр, публикация и история редакций. Восстановление предыдущей редакции. Не публикуй черновики через публичный API.
7. **Заявки**: предмет при наличии, имя, выбранный контакт, сообщение, время, статус обработки. Если форма использует согласие, сохраняй факт согласия и идентификатор неизменяемой редакции документа, показанной при отправке. Сбор только минимально необходимых данных.

### Глобальные настройки

- **Главная**: изображение первого экрана, focal point, заголовок, подпись, две кнопки, избранные предметы, история мастерской, порядок и видимость предусмотренных секций.
- **Мастерская**: текст, изображения, блок индивидуального заказа.
- **Оформление**: одна из трёх тем, логотип и favicon, безопасные контролируемые настройки акцента; проверяй контраст. Не давай ввод произвольного JavaScript или CSS.
- **Контакты и реквизиты**: телефон, email, адрес, социальные ссылки, сведения продавца. Выводить из общего источника; юридические тексты не переписывать автоматически при смене реквизитов.
- **Навигация и подвал**: пункты из существующих страниц, порядок, контакты, ссылки на документы.
- **SEO**: название сайта, метаданные по умолчанию, Open Graph изображение.

Все поля редактора снабди русскими названиями, подсказками и валидацией. Не перегружай владельца техническими полями. Типографика юридических страниц: ограниченная ширина строки, удобный основной шрифт, оглавление для длинного документа.

## Публикация и реальные данные

- Черновик не меняет публичную страницу. Предпросмотр доступен только авторизованному редактору.
- Публикация атомарно обновляет опубликованный снимок без нового деплоя; реализуй корректное сбрасывание клиентского кеша.
- Slug опубликованного документа стабилен. При изменении slug создай перенаправление или запрети изменение владельцу с понятным пояснением.
- Не ломай опубликованную страницу удалением используемой фотографии: покажи связанные записи и запрети удаление до замены ссылок.
- Не перезаписывай данные при рестарте, миграции или запуске seed. Seed явный, идемпотентный и содержит только демонстрационные данные.
- Не выдумывай настоящие названия моделей, цены, отзывы, награды, юридические условия или сведения компании. Неподтверждённые примеры пометь как демо. Не копируй изображения сайта без подтверждённого права использования. Для стартовой проверки используй локальные демо-изображения с понятным происхождением и возможность их заменить.
- Тексты документов предоставляются заказчиком. Демонстрационные документы не выдавай за готовые юридические документы; размещай как черновики.
- Стартовая тестовая среда: noindex. Noindex не является ограничением доступа. В обычном public GitHub Pages не обещай закрыть всю публичную оболочку паролем. Приватность черновиков реализуется на уровне API/Storage, а не JavaScript-экрана пароля. Hash routing и контент, загружаемый после запуска JS, ограничивают SEO и предпросмотр ссылок отдельных товаров в мессенджерах; честно документируй это. Для production SEO потребуется отдельное согласованное решение статической генерации.

## Безопасность данных и публикация

- SQL migrations для таблиц, связей, ограничений, ролей и RLS. Всем публично доступным таблицам включить RLS и настроить grants, не полагаться на скрытые кнопки.
- Анонимный пользователь читает только опубликованные снимки контента; не может создавать/изменять/удалять контент, читать черновики, историю, пользователей или заявки. Авторизованный пользователь без роли owner/developer также не имеет права редактирования.
- Таблица ролей не доступна для изменения owner; не доверять user_metadata, которое пользователь может менять. Проверить отсутствие рекурсии policies.
- Приватный bucket для исходников и черновиков; доступ только редакторам через policies/signed URLs. Public bucket только для медиа, явно предназначенных для публикации. При публикации подготовить публичные копии и ссылки, затем атомарно переключить снимок. При откате/снятии публикации объяснять, что уже скачанные публичные файлы отозвать нельзя.
- Документы и предметы: отдельные draft и published snapshot, редакции с неизменяемыми идентификаторами. Публикация и история через SQL transaction/RPC с проверкой роли и безопасным search_path; восстановление создаёт новую редакцию.
- Валидация данных в БД и API, обработка ошибок и конкурирующих изменений. Rich text безопасно рендерить; запрет raw JS и опасных URL.
- Не удалять используемые медиа, показать связанные записи. Не перезаписывать пользовательские данные при seed. Резервирование контента и файлов документировать отдельно; git не является бэкапом Supabase.
- Для первого демо формы реальных заявок отключены. Кнопки могут вести к контактам; не имитировать успешную отправку. Если реализуется сохранение заявок, использовать отдельную Supabase Edge Function с серверной валидацией, защитой от злоупотреблений и закрытыми правами чтения. Никаких SMTP-секретов в браузере. Реальные персональные данные не собирать до отдельного согласования инфраструктуры и правил обработки.
- Никаких встроенных паролей, открытого bootstrap, публичной регистрации или service_role в репозитории/клиенте.

## Настройка и документы для владельца

Создай README и `docs/SETUP_SUPABASE.md` с конкретными шагами: создать управляемый проект Supabase, применить migrations, настроить buckets/policies, отключить signup, создать пользователя owner и назначить роль, указать URL сайта и разрешённые redirect URLs Auth. Адрес должен включать фактический Pages base; проверить вход/выход, восстановление пароля если реализовано.

Параметры frontend: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_BASE_PATH` (либо эквивалентный согласованный набор). Не просить отправлять секреты в чат. Показать куда вводятся переменные сборки GitHub Actions и как включить Settings → Pages → GitHub Actions. Если план не поддерживает Pages private-репозитория, это отдельный понятный blocker; не менять видимость без поручения.

Добавь `docs/OWNER_GUIDE.md`: вход через адрес `…/Kilta/#/admin`, загрузка изображения, создание/публикация предмета, первый экран, документы, предпросмотр, восстановление редакции, темы. У владельца нет необходимости в GitHub или Supabase Dashboard.

Опиши ограничения и стоимость без обещаний бесплатности/бессрочности: тарифы, квоты и доступность Supabase и Pages проверяются перед подключением. Объясни, что без настроенного Supabase реально работающей общей админки не будет.

## Проверка готовности

- Typecheck, lint, статическая production build и запуск сборки под `/Kilta/`. Из build не должны требоваться Node.js runtime или Docker.
- Браузерные проверки 360, 768, 1440 px, три темы, клавиатура, отсутствие горизонтального скролла; прямые hash-ссылки работают после refresh.
- После настоящего подключения: owner входит, загружает фото, создаёт draft; анонимный посетитель не видит draft и приватное медиа даже прямым API-запросом.
- Публикация делает запись доступной с другого браузера после refresh. Правки draft не меняют прежний published snapshot. Изменения не требуют Actions build.
- Анонимный и посторонний authenticated пользователь не могут менять данные; owner не может назначить себе developer.
- Документ имеет историю; восстановление проверено; опубликованная ссылка стабильна.
- После повторного frontend-деплоя контент и фотографии остаются в Supabase.
- Проверить SQL/RLS и Storage allow/deny сценарии. При отсутствии внешних credentials выполнить доступные проверки, явно отметить непроверенные интеграционные сценарии; mock tests не выдавать за проверку реальной защиты.
- Демо-режим явно подписан, не показывает фиктивный успешный save. Показать данные пустого состояния, сетевую ошибку и отсутствие конфигурации.

## Порядок работы

Сначала прочитай репозиторий и действующие инструкции. Затем создай функциональный каркас с базой и админкой, проверенные права, каталог и медиа. После этого сделай дизайн, темы, документы и GitHub Pages deployment. Не заканчивай на красивом фронтенде с фиктивными кнопками. В финале укажи реализованное, результаты проверок, способ запуска и конкретные ограничения. Не меняй видимость репозитория, не раскрывай приватные материалы и не переключай домен без отдельного поручения. Работа считается завершённой только с честным перечнем выполненных и ещё не проверенных действий.
