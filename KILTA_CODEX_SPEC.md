# KILTA — задание для Codex

## Результат

Создай в этом репозитории работающий сайт авторской мебели и скульптур KILTA с настоящей русскоязычной админкой. Заказчик должен войти через браузер, загрузить свои фотографии и арты, наполнить каталог, изменить тексты и документы, выбрать оформление и опубликовать изменения без GitHub, терминала и помощи разработчика.

Репозиторий приватный. Сайт размещается отдельно и имеет доступный заказчику HTTPS-адрес. Не используй GitHub Pages как хостинг приложения. Не делай репозиторий публичным. Заказчик редактирует контент в базе данных, а не исходный код. Изменения контента не требуют коммита, сборки или деплоя.

Это задание на реализацию, а не только на план или статичный макет. Если внешние учётные записи и хостинг ещё не подключены, полностью реализуй и проверь проект локально, подготовь развёртывание и перечисли конкретные недостающие настройки. Не утверждай, что публичный сайт уже размещён.

## Стек

- Next.js с App Router, TypeScript и Payload CMS в одном приложении.
- PostgreSQL, официальный адаптер Payload.
- Встроенные средства Payload для пользователей, контроля доступа, медиа, черновиков и версий.
- CSS variables и Tailwind CSS либо CSS Modules; выбери один последовательный подход.
- Версии пакетов подбирай по актуальной официальной документации Payload и Next.js. Зафиксируй совместимые версии и lockfile, не используй произвольное сочетание latest.
- Для локального запуска: Docker Compose, приложение, PostgreSQL, постоянные volumes для БД и media.
- Для первого размещения на VPS: приложение в Docker, PostgreSQL и постоянный volume медиа. HTTPS через Caddy; hostname и секреты задаются окружением. База не доступна из интернета.
- Предусмотри замену файлового хранилища на S3-совместимое через официальный адаптер. S3 не должен быть обязательным для локальной проверки или первого VPS-деплоя.
- Не используй localStorage как источник данных сайта или имитацию базы. Не храни загруженные изображения только в памяти или во временном каталоге контейнера.

## Дизайн и страницы

Основа — концепт «Светлая галерея»: молочный фон #F5F3EE, графит #252525, крупные фотографии, выразительные заголовки, спокойные подписи, много пространства. Образцы макетов, если приложены, являются визуальными референсами, а не фоном страницы. Воспроизведи дизайн живыми компонентами.

Дополнительно реализуй темы «Тёплая мастерская» (песочный #E8DDCD, коричневый #49382C, терракотовые акценты) и «Тёмный арт-каталог» (угольный #171717, текст #EEE9DF, бронзовые акценты). Выбор активной темы — в админке. Общая структура сайта остаётся стабильной. Применяй тему без пересборки; проверяй контраст текста и кнопок во всех темах.

Страницы:
- Главная: меню, крупный первый экран с изображением и текстом, кнопки «Смотреть коллекцию» и «Обсудить заказ», избранные предметы, категории, семейная мастерская, индивидуальный заказ, шоурумы, подвал.
- Каталог с категориями и простыми фильтрами по наличию, материалу и диапазону цены. Предметы без открытой цены корректно показываются как «Цена по запросу».
- Карточка предмета: галерея, название, описание, материал, размеры, стоимость/цена по запросу, наличие, срок изготовления, индивидуальные варианты, кнопка обращения.
- Мастерская / о нас.
- Шоурумы: адреса, контакты, ссылка на маршрут, предметы в конкретном шоуруме. Внешняя карта загружается только по действию пользователя.
- Контакты.
- Документы: политика, согласие, оферта при необходимости, доставка и оплата, возврат и гарантия, реквизиты, информация о cookie.
- Страница 404, пустые состояния, обработка ошибок.
- Админка `/admin` с авторизацией.

Категории на старт: шезлонги, скульптуры, консоли, комоды, ширмы, столы, стеллажи, торшеры. Заказчик может менять список.

На телефоне используй удобное меню, читаемые подписи, адаптивную галерею, доступные кнопки. Не добавляй тяжёлое видео на первый экран, принудительную анимацию, декоративные заглушки вместо фотографий. Учитывай prefers-reduced-motion.

## Контент в CMS

### Коллекции

1. **Пользователи**: email, имя, роль `developer` / `owner`. Только developer управляет ролями и созданием пользователей. Owner управляет контентом и собственным профилем, не может назначить себе другую роль.
2. **Медиа**: файл, alt, подпись, автор/источник при необходимости, focal point. Загрузка JPEG, PNG, WebP и AVIF при поддержке используемого обработчика. Ограничение изображения 20 МБ, проверка MIME и фактического содержимого на сервере. SVG не принимать по умолчанию. Создавай оптимизированные размеры для карточек и первого экрана, сохраняй оригинал. Заказчик может загружать несколько файлов, выбирать существующие и менять порядок фотографий. PDF документов хранить отдельно с лимитом 10 МБ.
3. **Категории**: название, slug, изображение, описание, порядок, статус публикации.
4. **Предметы**: название, slug, категории, основное изображение, галерея, rich text описание, материалы, высота/ширина/глубина с единицами, режим цены (точная / от / по запросу), сумма, валюта RUB, наличие (в наличии / под заказ / продано), срок изготовления как текст, варианты исполнения, избранное, порядок, SEO. Черновики и версии.
5. **Шоурумы**: название, город, адрес, часы работы, контакты, фотографии, проверенная владельцем ссылка маршрута, связанные предметы, порядок, статус.
6. **Документы**: тип, название, slug, текст в rich text, дата редакции, дата вступления в действие, необязательный PDF, показывать в подвале, порядок. Черновики, предпросмотр, публикация и история редакций. Восстановление предыдущей редакции. Не публикуй черновики через публичный API.
7. **Заявки**: предмет при наличии, имя, выбранный контакт, сообщение, время, статус обработки. Если форма использует согласие, сохраняй факт согласия и идентификатор неизменяемой редакции документа, показанной при отправке. Сбор только минимально необходимых данных.

### Глобальные настройки

- **Главная**: изображение первого экрана, focal point, заголовок, подпись, две кнопки, избранные предметы, история мастерской, порядок и видимость предусмотренных секций.
- **Мастерская**: текст, изображения, блок индивидуального заказа.
- **Оформление**: одна из трёх тем, логотип и favicon, безопасные контролируемые настройки акцента; проверяй контраст. Не давай ввод произвольного JavaScript или CSS.
- **Контакты и реквизиты**: телефон, email, адрес, социальные ссылки, сведения продавца. Выводить из общего источника; юридические тексты не переписывать автоматически при смене реквизитов.
- **Навигация и подвал**: пункты из существующих страниц, порядок, контакты, ссылки на документы.
- **SEO**: название сайта, метаданные по умолчанию, Open Graph изображение.

Все поля редактора снабди русскими названиями, подсказками и валидацией. Не перегружай владельца техническими полями. Типографика юридических страниц: ограниченная ширина строки, удобный основной шрифт, оглавление для длинного документа.

## Публикация и реальные данные

- Черновик не меняет публичную страницу. Предпросмотр доступен только авторизованному редактору.
- Публикация обновляет публичное содержимое без нового деплоя; реализуй корректное сбрасывание кеша.
- Slug опубликованного документа стабилен. При изменении slug создай перенаправление или запрети изменение владельцу с понятным пояснением.
- Не ломай опубликованную страницу удалением используемой фотографии: покажи связанные записи и запрети удаление до замены ссылок.
- Не перезаписывай данные при рестарте, миграции или запуске seed. Seed явный, идемпотентный и содержит только демонстрационные данные.
- Не выдумывай настоящие названия моделей, цены, отзывы, награды, юридические условия или сведения компании. Неподтверждённые примеры пометь как демо. Не копируй изображения сайта без подтверждённого права использования. Для стартовой проверки используй локальные демо-изображения с понятным происхождением и возможность их заменить.
- Тексты документов предоставляются заказчиком. Демонстрационные документы не выдавай за готовые юридические документы; размещай как черновики.
- Стартовая тестовая среда: noindex, исключение черновиков и `/admin` из sitemap. Noindex не является ограничением доступа. Предусмотри опциональную защиту всего демо паролем на уровне reverse proxy, если заказчик хочет непубличный просмотр.

## Формы и доступ

- Сделай форму обращения, связанную с выбранным предметом; подписанные поля вместо одних placeholder.
- Перед отправкой показывай актуальные ссылки на применяемые документы. Если согласие предусмотрено формой, чекбокс не отмечен заранее; рассылка — отдельная необязательная настройка и согласие.
- Проверка входных данных и лимит частоты на сервере. Публичный посетитель может отправить обращение только через контролируемый endpoint и не может читать заявки.
- Пока правила обработки данных и рабочий хостинг не согласованы, демо-форму держать отключённой для реальных посетителей; включать через явную настройку окружения. Тестировать искусственными данными.
- Письма опциональны через SMTP. Если SMTP не подключён, не имитировать отправку: заявка сохраняется, пользователь получает корректное подтверждение сохранения.
- Публично доступны только опубликованные страницы, предметы, категории и предназначенные для публикации изображения. Черновики и медиа черновиков не должны раскрывать приватные материалы по прямому URL.
- Защищай действия реальными серверными правами Payload, а не только скрытыми кнопками. При Local API явно учитывай overrideAccess и user.
- Начальных пользователей создавай отдельной CLI-командой по значениям окружения. Без публичной регистрации, встроенного пароля или открытого bootstrap после деплоя.
- `.env` и секреты не коммитить. `.env.example` содержит только имена переменных и безопасные примеры. Не вставлять серверные секреты в клиентский bundle. Использовать штатные механизмы auth, CSRF и проверки origin Payload.

## Развёртывание и инструкции

Подготовь Dockerfile, compose для локальной проверки и compose/override для VPS, Caddyfile, healthcheck и миграции. Проверяй обязательные переменные при старте. База и медиа переживают перезапуск контейнеров и обновление приложения. Не выставляй dev-сервер в production.

Сделай README с командами запуска, подготовки env, миграций, явного seed, создания администратора, сборки, обновления и возврата к предыдущему образу с учётом совместимости БД. Добавь инструкции резервирования PostgreSQL и медиа и восстановления на тестовой среде. Secrets для GitHub Actions, если workflow используется, только через GitHub Secrets; публичный ключ/деплойный ключ не заменять секретом в коде. Деплой на VPS может быть сначала ручным; автоматический деплой не обязателен для работающего демо.

Добавь `docs/OWNER_GUIDE.md`: как войти, сменить первый экран, загрузить изображения, создать предмет, поменять цену, выбрать тему, изменить документ, проверить предпросмотр и опубликовать. Заказчику не требуется аккаунт GitHub.

## Проверка готовности

Проведи typecheck, lint и production build. Добавь осмысленные интеграционные проверки прав и браузерные проверки основного сценария. Минимальные критерии:

1. Owner входит, создаёт категорию и предмет, загружает фотографии, меняет порядок, сохраняет черновик, просматривает и публикует.
2. Предмет виден в публичном каталоге из другого браузера; после рестарта контейнеров он и фотографии сохраняются.
3. Изменение главного изображения, текста и темы через админку видно на публичном сайте без новой сборки.
4. Owner редактирует документ и публикует; старая редакция сохранена, ссылка остаётся рабочей.
5. Анонимный запрос к API не может менять данные, читать заявки/пользователей или раскрывать черновики. Owner не может повысить собственную роль.
6. Форма с искусственными данными сохраняет обращение, выбранный предмет и редакцию документа; ошибки не показывают ложный успех.
7. Прямой URL приватного файла черновика не раскрывает файл анонимному посетителю.
8. Проверены макеты 360, 768 и 1440 px, все три темы, клавиатурная навигация, фокус, контраст и отсутствие горизонтального скролла.
9. Миграции, seed и инструкция восстановления проверены; тестовые данные не перезаписывают контент заказчика.

## Порядок работы

Сначала прочитай репозиторий и действующие инструкции. Затем создай функциональный каркас с базой и админкой, проверенные права, каталог и медиа. После этого сделай дизайн, темы, документы, формы и deployment. Не заканчивай на красивом фронтенде с фиктивными кнопками. В финале укажи реализованное, результаты проверок, способ запуска и конкретные ограничения. Не публикуй репозиторий и не меняй внешний домен без отдельного поручения.
