# KILTA

React + TypeScript + Vite: публичный каталог и русскоязычная админка в одной **статической** сборке GitHub Pages. Supabase предоставляет Auth, PostgreSQL/Data API и Storage. Содержимое загружается при открытии сайта; публикация в админке не запускает GitHub Actions.

**GitHub Pages по умолчанию публикует демо без Supabase.** Каталог, страницы, мобильное меню и три темы доступны для просмотра. Авторизация, загрузки, сохранение и отправка заявок отключены; фотографии — лицензированные демонстрационные 3D-рендеры, не продукция KILTA. [Кнопки публикации демо и адрес сайта](docs/DEMO_PAGES.md).

Реализовано по [редакции 2 задания](KILTA_CODEX_SPEC.md). Предыдущий незавершённый прототип сохранён локально: коммит `3fd69b8`, ветка `archive/payload-prototype`. Из него адаптированы галерейный дизайн, адаптивные компоненты, три темы и структура страниц. Payload, Next.js, VPS и Docker deployment удалены из действующего приложения. Видимость репозитория не изменялась.

## Локальный запуск

Node.js 24 LTS (минимум 22.12), npm и браузер. Docker не нужен.

```sh
npm ci
cp .env.example .env.local
# Заполнить только публичные VITE_SUPABASE_URL и VITE_SUPABASE_PUBLISHABLE_KEY.
npm run dev
```

Проект по умолчанию использует base `/Kilta/`. Маршруты: `/Kilta/#/`, `/Kilta/#/catalog`, `/Kilta/#/products/slug`, `/Kilta/#/admin`. Для корневого сайта/custom domain задайте `VITE_BASE_PATH=/` перед сборкой; домен автоматически не переключается.

Без подключения: показываются явное уведомление и пустые состояния; вход и сохранение недоступны. Для отдельного **read-only** демо:

```sh
VITE_DEMO_MODE=true npm run dev
```

Демо включается только при отсутствии корректной конфигурации Supabase. Не имитирует авторизацию/запись и не хранит контент в localStorage. Supabase Auth может хранить сессию в браузере; это не хранилище каталога. Демо-рендеры мебели имеют CC0/CC BY 4.0 лицензии, происхождение сохранено в `public/demo/LICENSE.txt`; это не изделия KILTA.

## Подключение и публикация

Следуйте [SETUP_SUPABASE](docs/SETUP_SUPABASE.md): управляемый проект, SQL-миграция, buckets/policies, отключение signup, создание пользователей и назначение ролей, Auth URL. Никакого открытого bootstrap или service_role в клиенте нет.

В Settings → Secrets and variables → Actions → **Variables** задайте:

| Переменная                      | Значение                                                       |
| ------------------------------- | -------------------------------------------------------------- |
| `VITE_SUPABASE_URL`             | HTTPS URL проекта                                              |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный publishable key или legacy anon key                  |
| `VITE_BASE_PATH`                | `/Kilta/` (или `/` только для согласованного корневого домена) |

Public key станет виден в bundle; безопасность обеспечивается RLS и Storage policies. `service_role`, `sb_secret_*`, пароли БД, SMTP-секреты никогда не помещать в `VITE_*`. Сборка отказывается принимать известные секретные ключи.

Settings → Pages → Source: **GitHub Actions**. [Workflow](.github/workflows/pages.yml) при push в `main`/ручном запуске выполняет `npm ci`, typecheck, lint, unit tests, build и deploy официальными Pages actions. PR выполняет проверки и сборку демо, без публикации. Загружается только `dist/`, не SQL, исходные приватные фотографии или `.env`.

По умолчанию push собирает `demo`: `VITE_DEMO_MODE=true`, URL/key пустые, Supabase не требуется. Для реального сайта после настройки проекта выберите **supabase** в Workflow dispatch; для следующих push задайте Actions Variable `KILTA_DEPLOY_MODE=supabase`. В этом режиме отсутствующие или секретные ключи останавливают сборку. Значение по умолчанию `KILTA_DEPLOY_MODE` — `demo`; ручной выбор режима имеет приоритет. Не переключайте на supabase до проверки Auth/RLS/Storage.

Для Pages текущего private-репозитория нужен подходящий GitHub план владельца/организации. Если он недоступен, публикация заблокирована: смена видимости и отдельный public-репозиторий требуют отдельного решения владельца. Исходный private-код и публично доступный JS bundle — разные вещи.

## Проверки

Результаты и границы выполненных проверок: [VERIFICATION](docs/VERIFICATION.md).

```sh
npm run typecheck
npm run lint
npm test
npm run build
npm run preview
npm run test:e2e
```

Сборка по `/Kilta/` — обычные HTML/CSS/JS/assets, без Node.js runtime на хостинге. `test:e2e` использует установленный Chromium (`CHROMIUM_PATH`, по умолчанию `/usr/bin/chromium`); локально можно установить Chromium через Playwright и указать путь. Браузерные тесты запускают production builds, проверяют 360/768/1440 px, темы, фокус, hash refresh и сценарии редактора. Supabase transport в них подменяется: **это проверки интерфейса, а не доказательство облачной авторизации или Storage**.

```sh
# Только изолированный/local PostgreSQL SUPERUSER тестовый адрес.
# Создаёт и удаляет отдельную базу; production запрещён.
TEST_DATABASE_URL='...' npm run test:sql
# После подключения отдельного Supabase тестового проекта:
TEST_ALLOW_WRITES=true npm run test:live
```

SQL-тесты применяют настоящую миграцию и исполняют PostgreSQL RLS/RPC под `anon`, `authenticated`, owner и developer. Таблицы `auth`/`storage` в них — тестовые fixtures: JWT выдача, REST gateway, фактическое хранение файлов и MIME/size enforcement Supabase не проверяются этим тестом. Для проверки облака нужны реальные параметры из `.env.local`/защищённого окружения и отдельный тестовый проект. Live-тесты создают искусственные данные, не предназначены для production.

## Как устроена публикация

`content` содержит приватные черновики; `published_content` — отдельные публичные снимки. `versions` сохраняет каждое сохранение, публикацию и восстановление. Редактор вызывает role-checked RPC с ожидаемой редакцией: устаревшие/конкурирующие изменения отклоняются. Публикация атомарно меняет снимок и фиксирует новую редакцию. Восстановление создаёт новый черновик; публичная страница меняется только после публикации.

Оригиналы/производные — в приватных buckets. При публикации браузер готовит неизменяемые публичные копии, затем SQL проверяет их наличие и переключает снимок. Если подготовка/транзакция не завершились, прежний снимок сохраняется, но уже подготовленные публичные копии могут остаться доступными. Публиковать следует только разрешённые материалы. Публичный bucket **не может обеспечить отзыв уже скачанного файла**. Снятие публикации убирает запись из Data API; исторические публичные копии остаются. Удаление используемых файлов запрещено и через БД, и через Storage policies; история редакций также удерживает ссылки.

Опубликованный slug документа неизменяем. Приватные signed URLs выдаются редакторам на пять минут и обновляются во время работы медиатеки. Интерфейс владельца: [OWNER_GUIDE](docs/OWNER_GUIDE.md). Резервирование отдельно от Git: [BACKUP](docs/BACKUP.md).

## Ограничения

- Без реального проекта Supabase общей работающей админки и межустройственного сохранения нет. Текущие облачные credentials не предоставлены; реальные Auth/Data API/Storage сценарии не проверены.
- Storage проверяет разрешённый MIME и размер на сервере. Magic bytes, декодирование и WebP выполняются в браузере. Полная серверная проверка фактических байтов/декодирование/антивирус **не реализованы**; обход клиентских проверок возможен для редактора с прямым API-доступом. При необходимости добавляется согласованная Edge Function до допуска загрузок.
- Публичная форма заявок отключена; отправка и SMTP не имитируются. Для её подключения нужны согласование обработки персональных данных и серверная Edge Function с валидацией/антиспамом. RLS закрывает таблицу заявок для посетителей.
- Нет подписок на live-изменения: другой посетитель видит публикацию после обновления страницы. Открытая вкладка не обновляется мгновенно.
- Стартовая версия `noindex`. Hash routing и данные после JS ограничивают SEO/OG отдельных предметов. Для production SEO нужна отдельная согласованная статическая генерация; пароль на всю public Pages оболочку не обещается.
- Расценки, квоты, резервирование и доступность Supabase и Pages зависят от актуальных планов. Бесплатность/бессрочность не обещаются; тариф и регион проверяются до подключения.
